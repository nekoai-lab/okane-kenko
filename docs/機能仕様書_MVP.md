## 3. 入力ウィザード仕様

### 3.1 設計方針

- 1画面1テーマ。必須設問は12問以内（FR-10）。
- 実額入力を求めない。**レンジ選択**が原則（DR-02）。
- すべての設問に「答えたくない／分からない」を用意し、正規値として保存（DR-03）。
- 各ステップ遷移でイベント送出（DR-04）。

### 3.2 ステップと設問

| Step | 設問 | 形式 | 必須 | 欠損時の扱い |
|---|---|---|---|---|
| S1 | 本人の生年 | 年プルダウン | ✓ | 不可（算定の起点）。性別は集めない（算定エンジンが使わないため。将来 AI 個別化で必要になれば追加） |
| S1 | 就業形態 | 会社員／公務員／自営・フリーランス | ✓ | 会社員で仮置き＋推定フラグ |
| S2 | 配偶者の有無・生年・就業状況 | 選択 | ✓ | 「なし」で分岐 |
| S2 | 子の人数・各子の生年 | 人数＋生年プルダウン | ✓ | 「なし」で分岐 |
| S3 | 本人の年収 | レンジ：〜400／〜600／〜800／〜1000／1000万+／答えたくない | ✓ | 答えたくない→区分エ相当で仮置き＋推定フラグ |
| S3 | 配偶者の年収 | 同上＋「収入なし」 | 配偶者ありなら✓ | 同上 |
| S4 | 金融資産（世帯合計） | レンジ：〜100／〜300／〜500／〜1000／1000万+／分からない | ✓ | 300万で仮置き＋推定フラグ |
| S4 | 毎月の生活費 | レンジ：〜20／〜25／〜30／〜35／35万+／**年収から推定してもらう** | ✓ | 推定式（§4.2.1） |
| S5 | 住まい | 持ち家（ローンあり／なし）／賃貸 | ✓ | ― |
| S5 | ローン残高＋団信の有無 | レンジ＋有／無／分からない（1行解説つき） | ローンありなら✓ | 「分からない」→**団信ありで算定し、その旨を結果に明記** |
| S5 | 家賃 | レンジ | 賃貸なら✓ | 生活費に含む扱い |
| S6 | 現在加入中の保険 ★最重要 | ①証券の写真アップ ②手入力（種類・保障額・月額保険料） ③**分からない** | ✓（③可） | ③→過不足判定を保留し必要額のみ提示（FR-14） |
| S6 | 手入力の最小形 | 「月額保険料の合計だけ」でも受け付ける | ― | 種類不明として扱う |
| S7 | 傷病手当金・団信・高額療養費の認知 | 知っている／聞いたことがある／知らない（各1問） | ― | 言語化の説明の詳しさを切り替える（説明の個別化に使用） |

**S6の3経路（FR-07）**：
- ①写真：抽出項目＝保険種類／死亡保障額／入院日額／月額保険料／契約日。抽出は補助であり、**抽出結果を必ずユーザーに確認させて確定する**（誤読の責任を本人確認で担保。OI-05）。原本は24時間以内に削除（DR-06）。
  - 抽出は**言語化とは別のLLM呼び出し**であり、責務・プロンプト・ガードレールを分離する（§3.4）。
- ②手入力：1件ずつ追加。最小は「月額保険料の合計」だけ。
- ③分からない：`current_coverage.status = "unknown"` として先へ進む。

### 3.3 証券写真からの抽出（LLM呼び出し①）

言語化（LLM呼び出し②・§5）とは**役割・入出力・失敗時挙動が異なる**ため、別コンポーネントとして定義する。

| 項目 | 内容 |
|---|---|
| 役割 | 画像1枚から保険契約の項目を**転記**する。解釈・推測・補完をしない |
| 入力 | 証券画像（GCS署名付きURL）＋抽出対象項目リスト |
| 出力 | `ExtractedPolicy[]`（下記） |
| 禁止 | 読み取れない項目を推測で埋める／保障内容の評価コメントを付ける |
| 失敗時 | 手入力（②）へフォールバック。「読み取れませんでした」と明示し、責任を本人に戻す |

```json
{
  "policies": [
    {
      "insurer": "string|null",
      "product_type": "death_term | death_whole | medical | cancer | income | unknown",
      "death_benefit": 0,
      "hospital_daily": 0,
      "monthly_premium": 0,
      "contract_date": "YYYY-MM|null",
      "confidence": "high | low",
      "unreadable_fields": ["string"]
    }
  ]
}
```

**抽出側ガードレール**

| # | 検査 | 不合格時 |
|---|---|---|
| X-1 | `confidence: low` または `unreadable_fields` が空でない | 該当項目を空欄にしてユーザー確認画面へ（自動確定しない） |
| X-2 | `death_benefit > 3億` / `monthly_premium > 50万` | 桁誤読として空欄化 |
| X-3 | 出力に自由記述の評価文が含まれる | 破棄（スキーマ外の値は無視） |

> **設計理由**：転記（①）と翻訳（②）を1つのプロンプトに混ぜると、読み取り失敗が説明文の推測に伝播する。分離すれば、抽出が失敗しても手入力に落ちるだけで診断は成立する。

### 3.4 バリデーション

| 対象 | ルール | エラー時 |
|---|---|---|
| 生年 | 1940〜当年。本人18歳以上 | インラインで再入力 |
| 子の生年 | 本人生年より後、0〜30歳 | 同上 |

## 4. 算定エンジン仕様（決定的ロジック）

> **原則**：ここに書かれた式のみで金額が決まる。AIは介在しない。同一入力＋同一パラメータ版で必ず同一結果（AR-06）。

### 4.1 算定対象と出力

MVPの算定対象は2つ：**(A) 必要死亡保障額**（本人が亡くなった場合）と **(B) 医療保障の過不足**。

出力（`DiagnosisResult`）は §6.1 のスキーマに従い、**すべての中間項目を金額つきで保持**する（FR-12。言語化とガードレールの両方がこれを参照する）。

### 4.2 (A) 必要死亡保障額

```
必要額_raw = max(0, 支出見込 E − 収入・資産見込 I)
E = E1 + E2 + E3 + E4
I = I1 + I2 + I3 + I4 + I5
```

**期間の定義**

| 記号 | 定義 |
|---|---|
| `Y_total` | **算定期間 ＝ 遺された配偶者が65歳になるまでの年数**（独身は0） |
| `Y_dep` | 子育て期間 ＝ 末子が22歳になるまでの年数（`Y_total` で頭打ち。子なしは0） |
| `Y_alone` | 末子独立後の期間 ＝ `Y_total − Y_dep` |
| `Y_child(i)` | 子iが18歳到達年度末までの年数（遺族基礎年金用） |

> **算定期間の考え方（ADR-008 / grill Q3・Q3-b）**：期間は**一律「配偶者65歳まで」**とし、就業状況で期間を分岐させない。分岐すると境界の両側（配偶者年収129万円と131万円）で必要額が約1,800万円変わる崖ができ、正直さとして耐えられないため。就業状況の違いは、**期間ではなく就労収入の控除額（§4.2.5 I3）で連続的に反映する**。

> **実装の正本**：本節のロジックは `calc.py`（算定エンジン参照実装）と `算定テスト_10世帯.xlsx`（10世帯・19死亡ケースの検算結果）に一致させること。式を変えたら必ず両方を更新する。

#### 4.2.1 E1 遺族の生活費

```
月間生活費 M = 選択レンジの中央値
  （「年収から推定」を選んだ場合： M = 世帯手取り年収 × 0.75 / 12 ）

E1a（子育て期）     = M × 0.70 × 12 × Y_dep
E1b（末子独立後）   = M × 0.50 × 12 × Y_alone
E1 = E1a + E1b
```
- `0.70` `0.50` = 遺族生活費率（子育て期／独立後）。**いずれも公的出典のない当社基準**。パラメータ化し、結果画面で本人が動かせるようにする（ADR-014）。
- 賃貸の場合、家賃は M に含める（E3で二重計上しない）。

#### 4.2.2 E2 教育費（段階別）

子の現年齢から独立（22歳）まで、**残りの各年を学齢段階に割り当てて実額を積む**。

```
E2 = Σ_i Σ_{a=子iの現年齢}^{21} 段階別年額(a, 進路) × 地域係数
```

- **段階別年額は文科省「子供の学習費調査」の「学習費総額」**（授業料だけでなく、塾＝補助学習費・部活＝教科外活動費・行事・修学旅行・制服・寄付を**含む実支出**）。値は `params.education.stages`。
- **高校（15〜17歳）は就学支援金を年ごとに控除**（`params.education.shien`。公立/私立の別。高校無償化・所得制限なし）。
- **大学（18〜21歳）は4年総額÷4の年額換算**（国立／私立文系／私立理系。`params.education.university`）。入学料は年額換算に含める。
- **地域係数**（`params.education.regionFactor`）は当面 1.0（全国平均）。将来 都市階級別で係数化。

進路シナリオを1つ選択（既定＝公立中心）。「まだ決めていない」は公立中心で仮置きし推定フラグを立てる。各シナリオは段階別の公立/私立パターンに展開する（`params.education.presets`）：

| シナリオ | 幼 | 小 | 中 | 高 | 大 |
|---|---|---|---|---|---|
| 公立中心 | 公立 | 公立 | 公立 | 公立 | 国立 |
| 私立混在 | 私立 | 公立 | 公立 | 私立 | 私立文系 |
| 私立中心 | 私立 | 私立 | 私立 | 私立 | 私立理系 |

> 旧モデル（進路ごとに丸めた総額 1,000/1,500/2,000万円を `(22−age)/22` で按分）は、近い高額段階（高校・大学）を過小評価していたため、段階別の実額積み上げに置き換えた（出典＝令和5年度子供の学習費調査）。

#### 4.2.3 E3 住居費

| 条件 | E3 |
|---|---|
| 持ち家・ローンあり・**団信あり**（または「分からない」） | **0**（ローンは団信で消滅） |
| 持ち家・ローンあり・団信なし | ローン残高（レンジ中央値） |
| 持ち家・ローンなし | 0 |
| 賃貸 | 0（家賃はE1のMに含む） |

#### 4.2.4 E4 葬儀・予備費

`E4 = 200万円`（パラメータ `funeral_reserve`）

#### 4.2.5 I 収入・資産見込

**I1 遺族基礎年金**

```
I1 = Σ_年 ( 基本額 + Σ_i 子加算(i) )   ※子iが18歳到達年度末まで
子加算(i) = 第1子・第2子 → child_add_1_2 ／ 第3子以降 → child_add_3plus
```

**I2 遺族厚生年金**

```
平均標準報酬額 ≈ 年収レンジ中央値 / 12
報酬比例年金額 = 平均標準報酬額 × 5.481/1000 × 被保険者月数
  ※ 被保険者月数 < 300 のときは 300 とみなす（短期要件のみなし300月）
遺族厚生年金(年額) = 報酬比例年金額 × 3/4
I2 = 遺族厚生年金(年額) × 受給想定年数
```
- 受給想定年数：**子あり配偶者** → `Y_total`／**子なし配偶者** → §4.2.6（2028年改正で原則5年）
- 自営・フリーランス（第1号被保険者）は厚生年金の被保険者期間がない前提で `I2 = 0`（過去の会社員期間は MVP では考慮しない。結果に明記）

**I2b 中高齢寡婦加算**

```
子あり： 遺族基礎年金の受給終了後〜65歳のうち、配偶者が40歳以上である各年に加算
子なし： 死亡時に配偶者が40歳以上である場合のみ、Y_total にわたり加算（40歳未満なら0）
```
> ⚠ 当初実装では子なし世帯でも一律に加算していたため、30代の配偶者に受給資格のない加算が乗っていた（10世帯テストで検出・修正済み）。**性別・年齢要件の細目は一次情報で要確認。**

**I3 遺族の就労収入（連続推定 ― ADR-008）**

```
現在の手取り  net_now   = 配偶者年収レンジ中央値 × 0.80
独立後の推定  net_after = max(net_now, post_indep_min_income)   ※既定 100万円/年

I3 = net_now × Y_dep  +  net_after × Y_alone
```
- 専業（年収0）でも、末子独立後はパート相当（年100万円）で働ける前提を**最低額**として置く。共働きなら `net_now` がそのまま伸びるので、境界に崖ができない。
- **全額を必要保障から差し引く**（ADR-009）。この設計が結論を最も大きく動かす前提であり、差し引かない設計にすると結果は真逆になる。
- `post_indep_min_income = 100万円` は当社基準（出典なし）。

**I4 金融資産** = レンジ中央値

**I5 死亡退職金・弔慰金** = 任意入力（既定0。会社員は S7 で「分からない」が多い想定のため既定0のまま）

#### 4.2.6 子なし世帯の分岐（2028年改正の影響を受ける層）

子なし配偶者は遺族基礎年金を受けられず、**2028年4月以降は遺族厚生年金が原則5年の有期給付**となる。

```
I1 = 0
I2 = 遺族厚生年金(年額) × 5     ※2028年4月以降に受給開始する場合
E1 = M × 0.70 × 12 × min(Y_spouse, living_support_years)   ※既定 living_support_years = 10
```
判定結果に `pension_reform_2028.applicable = true` を立て、言語化で必ず言及する（FR-17）。

#### 4.2.7 レンジ化と充足判定（FR-16 / FR-19）

```
margin = I − E

if 必要額_raw ≧ 300万:
    提示レンジ = [ round100(必要額_raw × 0.8), round100(必要額_raw × 1.2) ]
    verdict = "shortage"

elif 扶養家族がいない（独身・配偶者も子もなし）:
    提示レンジ = [ round100(E4), round100(E4) ]        # 葬儀・予備費のみ
    verdict = "not_needed"                            # 「保障は要りません」

elif margin > E × 0.2:
    提示レンジ = [ round100(E4), round100(E4) ]
    verdict = "ample"                                 # 「上乗せも要りません」

else:
    上乗せ下限 = round100(E4 + M × 0.70 × 12)          # 葬儀・予備費 + 生活立て直し12ヶ月
    上乗せ上限 = round100(E4 + M × 0.70 × 24)          # 同 24ヶ月
    提示レンジ = [上乗せ下限, 上乗せ上限]
    verdict = "sufficient"                            # 「安心の上乗せ」目安を出す
```
`round100` = 100万円単位に丸め。

> **`not_needed` と `ample` を分けた理由**：当初は充足時に一律で「安心の上乗せ」を提示していたため、**独身者や、収入・資産が支出を大きく上回る世帯にまで上乗せを勧めていた**（10世帯テストで検出）。これは煽りであり、芯に反する。余剰が大きいときは「上乗せも要りません」と言い切る。

**現在の保障との比較**（`current_coverage.status != "unknown"` のとき）

| 条件 | 判定 |
|---|---|
| 現保障額 < 提示レンジ下限 | `shortage`（不足額＝下限 − 現保障額） |
| 提示レンジ内 | `adequate` |
| 現保障額 > 提示レンジ上限 × 1.5 | `excess`（減額余地＝現保障額 − 上限） |

### 4.3 (B) 医療保障の過不足

```
所得区分 = 年収レンジ → 高額療養費の区分（ア〜オ）
月額自己負担上限 = パラメータ表の該当区分の式に医療費100万円を代入した値

標準ケース  burden_std  = 月額上限 × 1ヶ月 + 保険外費用(月10万 × 1)   # 患者調査 平均在院日数ベース
長期化ケース burden_long = 月額上限 × 3ヶ月 + 保険外費用(月10万 × 3)

判定（長期化ケースを基準にする）：
  金融資産 ≧ burden_long × 3  → "self_insurable"（減らせる候補）
  burden_long ≦ 資産 < ×3     → "partial"
  金融資産 < burden_long       → "needed"
```
> ADR-010：入院期間は**厚労省 患者調査の平均在院日数**、保険外費用は民間の大規模調査に差し替える（いずれも要一次情報確認）。**資産倍率3倍だけは公的な裏付けがないので「当社基準」と明示**し、出典欄と並べて表示する。
`self_insurable` かつ現在の医療保険料が計上されている場合、**「入らなくていい」候補として必ず提示**（AR-05）。

### 4.4 制度改正の該当判定（FR-17）

| 改正 | 判定ロジック | 提示 |
|---|---|---|
| 遺族厚生年金の有期化（2028年4月〜） | 子あり配偶者 → `applicable = false`／子なし配偶者 → `true` | falseなら「あなたの世帯は当面これまで通り。煽りは無視してよい」 |
| 高額療養費の上限引き上げ（2026年8月〜、2027年8月に区分細分化） | 所得区分から改正前後の上限差を算出 | 「月あたり最大 +X円」を提示 |

### 4.5 丸めと表示規則

- 内部計算は円単位、表示は**万円単位・100万円丸め**（レンジ提示のため）。
- 「約」を必ず付す。単一値の断定表示を禁止（FR-16 / CR-04）。

## 5. 言語化仕様（AI）

### 5.1 責務

AIがやること＝**算定結果の翻訳**。やらないこと＝金額の算出・商品の推奨・将来予測。

### 5.2 入力（算定エンジン → LLM）

`DiagnosisResult`（§6.1）から、氏名等の識別情報を除いた構造化JSONのみを渡す（AR-09）。加えて S7 の認知度回答を「説明の詳しさ」制御に使う。

### 5.3 出力スキーマ（構造化出力を強制）

```json
{
  "headline": "string  // 冒頭の結論。1文",
  "verdict_label": "sufficient | shortage | excess",
  "breakdown_narrative": "string  // なぜこの額か。内訳3要素以上に言及",
  "reform_note": { "text": "string", "citations": ["string"] },
  "reduce_note":  { "text": "string", "citations": ["string"] },
  "next_steps":   ["string"],
  "disclaimer": "string",
  "used_numbers": [ { "label": "string", "value": 0 } ]
}
```
`used_numbers` に、本文で使った数値をすべて申告させる。ガードレールはこれと算定結果を突合する。

### 5.4 プロンプトの組み立て順序（静的 → 動的）

トークンキャッシュを効かせ、コスト目標（NFR-12：1診断10円以内）を守るため、**変わらないものを前・変わるものを後**に置く。

| 順 | ブロック | 静/動 | 内容 | 更新単位 |
|---|---|---|---|---|
| 1 | システムプロンプト | 静 | §5.5の絶対規則＋文体。**デプロイ単位でのみ変更** | リリース |
| 2 | 出力スキーマ定義 | 静 | §5.3 | リリース |
| 3 | 用語注釈の辞書（団信・遺族厚生年金・高額療養費など） | 静 | 初出注釈のひな型 | リリース |
| 4 | RAG検索結果（参考資料） | 動 | 有効期間フィルタ済みチャンク | 診断ごと |
| 5 | 算定結果JSON（`DiagnosisResult`） | 動 | §6.1 | 診断ごと |
| 6 | 個別化指示 | 動 | S7の認知度に応じた「この用語は詳しく／簡潔に」の1〜3行 | 診断ごと |

**やらないこと**

- セッション中のモデル切り替えはしない。`504 AI_TIMEOUT` 時も**別モデルへ切り替えず、算定結果のみ表示**する（§7）。切り替えはキャッシュを捨て挙動の再現性も失う。
- 禁止語辞書（商品名20種など）を**プロンプトに入れない**。G-2は出力後の検査で行うため、プロンプトに載せると毎回トークンを払う上に、禁止語を提示することで逆に出現を誘発しうる。
- 個別化指示（6）で規則を上書きしない。規則は常に静的ブロックが優先。

### 5.5 システムプロンプト骨子

```
あなたは公的保障と家計の「翻訳者」です。判断者ではありません。

# 絶対規則
1. 金額・年数・割合は、入力JSONに存在する値のみを使う。計算・推定・丸め直しをしない。
2. 保険商品の名称を出さない。加入・申込を勧める表現を使わない。
3. 不安を煽らない。「大変なことになる」「今すぐ」等の圧をかける表現を使わない。
4. 公的制度に言及する文には、渡された参考資料の出典を citations に入れる。出典が無い制度の話はしない。
5. 断定的な将来予測をしない。「概算」「目安」であることを保つ。
6. 減らせる箇所（reduce_note）は、入力JSONの excess / self_insurable がある場合は必ず書く。
   無い場合は「今回、減らせる箇所は見つかりませんでした」と正直に書く。
7. 家計全体の最適化・投資助言はしない。求められても「この診断の範囲外です」と述べる。

# 文体
中学生が読める語彙。専門用語（団信・遺族厚生年金・高額療養費）は初出で1行注釈。
「あなたの世帯では」で始め、一般論を語らない。
```

### 5.6 ガードレール（AR-02〜AR-05）

| # | 検査 | 不合格時 |
|---|---|---|
| G-1 | 出力本文から数値トークンを抽出し、`DiagnosisResult` の値集合（および `used_numbers`）に存在しない数値がないか照合。許容誤差0 | 再生成（最大2回）→ テンプレート文にフォールバック |
| G-2 | 禁止語リスト（商品名辞書／「加入しましょう」「今すぐ」「絶対」「必ず得」「最も安い」等）に一致 | 再生成 → フォールバック |
| G-3 | `reform_note` / `reduce_note` に制度言及があるのに `citations` が空 | 該当セクションを削除して出力 |
| G-4 | `verdict_label` が算定エンジンの `verdict` と不一致 | 再生成（一致するまで）→ フォールバック |
| G-5 | `excess` / `self_insurable` があるのに `reduce_note` が空 | 再生成 |
| G-6 | 出力に投資商品・銘柄・利回りの言及（CR-05） | 該当文を削除 |

**フォールバック**：算定結果を差し込んだ固定テンプレート文を表示し、`fallback: true` を記録。運営レビューキューに上げる（AR-07）。**MVPでは全件レビュー**。

### 5.7 RAG仕様

| 項目 | 内容 |
|---|---|
| 対象文書 | 日本年金機構「遺族年金ガイド（年度版）」、厚労省 高額療養費の告示・リーフレット、遺族厚生年金改正の説明資料、傷病手当金の解説、団体信用生命保険の一般解説 |
| 保管 | Vertex AI Vector Search。チャンク 500〜800字、オーバーラップ100字 |
| メタデータ | `doc_id / title / publisher / fiscal_year / effective_from / effective_to / url` |
| 検索 | `effective_from ≦ 算定基準日 ≦ effective_to` でフィルタしてから類似検索（PR-07。改正前文書を引かない） |
| 引用形式 | 「出典：日本年金機構『遺族年金ガイド 令和8年度版』」＋URL |
| 商品情報 | **MVPでは知識ベースに含めない**（CR-01。商品を語れる状態にしない） |

| PATCH | `/api/sessions/{id}/answers` | 部分保存。`{step, answers}` |

### 7.1 取り消せない操作の扱い

以下は「実行すると元に戻せない／全診断に波及する」操作であり、汎用のDB操作やスクリプト実行（bash等）で行わず、**専用の操作として実装し、確認・監査・ゲートを付ける**。

| 操作 | なぜ危険か | required |
|---|---|---|
| 制度パラメータ版の有効化 | 誤値を入れると**以後すべての診断が静かに間違う**。事業の芯（正直さ）を最も直接的に壊す | ①差分プレビュー表示 ②ゴールデンテスト GT-01〜GT-10 の自動再実行に合格しないと有効化不可 ③実行者と承認者が別人（二人承認） ④監査ログ |
| 本人データ全削除（`DELETE /api/me`） | 復元不可 | ①削除される内容の一覧提示 ②文字入力による確認 ③削除完了通知 ④監査ログ（何を消したかの件数のみ） |
| 証券画像の削除（TTL） | 復元不可 | 自動実行。削除実行ログを残す |
| BigQueryへのストリーム | 一度出したデータは回収困難 | 送出前にスキーマ検査（実額・氏名が含まれないこと）を通す。検査失敗は送出せずアラート |
| インセンティブ（ギフト）配布 | 金銭が動く／取り消せない | **MVPでは自動化しない**（運営が手動配布。CR-10） |

> 逆に、**LLMには一切の副作用を持たせない**（外部送信・DB書き込み・削除のツールを渡さない）。LLMの出力は「文章」のみで、保存はアプリ側が行う。これによりガードレール不合格時に破棄するだけで済む。

**`POST /api/diagnose` の処理順**

1. 入力の完全性チェック → 欠損は既定値で補い `assumptions[]` に理由を記録
2. パラメータ版のロードと有効期限チェック（PR-04。期限切れ中核パラメータなら `503 PARAM_EXPIRED`）
3. 算定エンジン実行（純粋関数・1秒以内）
4. RAG検索（有効期間フィルタ込み）
5. Gemini 呼び出し（構造化出力）
6. ガードレール G-1〜G-6 → 不合格は再生成／フォールバック
7. Firestore 保存 → BigQuery ストリーム → 応答

**エラーコード**

| コード | 意味 | 画面挙動 |
|---|---|---|
| `400 INCOMPLETE_INPUT` | 必須未入力 | 該当ステップへ戻す |
| `503 PARAM_EXPIRED` | 制度パラメータ期限切れ | 「制度改正の反映中」表示。診断させない |
| `504 AI_TIMEOUT` | 言語化タイムアウト | **算定結果（数値と内訳）のみ先に表示**し、説明文は後追い |
| `500 GUARDRAIL_FAILED` | 再生成2回失敗 | テンプレート文で表示＋レビューキュー |

> `504` の挙動は重要：**数値は算定エンジンが持っているのでAIが落ちても診断は成立する**。この分離が可用性の担保でもある。

## 9. エッジケースと挙動

| # | ケース | 挙動 |
|---|---|---|
| 1 | 独身・扶養なし | 必要死亡保障は葬儀・予備費のみ。「保障はほぼ不要」と正直に言う。医療判定のみ実施 |
| 2 | 子なし夫婦（DINKs） | §4.2.6ルート。2028年改正の該当を明示（この層が唯一の直撃層） |
| 3 | 子が既に22歳以上のみ | `Y_dep = 0`。子なし扱いに準ずる |
| 4 | 配偶者の収入が本人より高い | 算定は「本人が亡くなった場合」のまま。結果に「配偶者側の診断も推奨」と付記（相互診断はPhase2） |
| 5 | 自営・フリーランス | `I2 = 0`、傷病手当金なしとして扱い、その差を明示 |
| 6 | 団信「分からない」 | 団信ありで算定し、**「団信がない場合は必要額が◯万円増えます」を併記** |
| 7 | 保険内容「分からない」 | 必要額のみ提示。過不足判定は `pending` として「証券が見つかったら再診断できます」 |
| 8 | 現保障が極端に多い（10倍以上） | `excess` として提示。ただし解約返戻金・貯蓄性の可能性に触れ、「一律の解約は勧めない」と明記 |
| 9 | 年収「答えたくない」 | 区分エ相当で仮置き。`assumptions[]` に記録し、結果に「収入未入力のため概算幅が広い」と表示 |

5. 計測イベント→BigQuery→完走率/離脱率の集計
6. 運営レビュー画面（P-90）
7. RAG（出典表示）

## 12. モデル依存の設計判断と見直しトリガー（陳腐化管理）

本仕様には「今のモデルの弱点を補うための処理」と「モデルが賢くなっても外せない処理」が混在している。**両者を混同すると、不要な処理を永久に抱えるか、外してはいけない処理を外す**。区別して記録する。

| 処理 | 前提 | 恒久 / 暫定 | 見直しトリガー |
|---|---|---|---|
| G-1 数値照合（AI出力の数値を算定値と突合） | モデル能力ではなく、**「金額を創らせない」ことを事後に立証する法令・信頼上の要請**（CR-09） | **恒久** | 外さない。モデル更新でも維持 |
| G-2 禁止語検査 | 同上（募集行為との線引きの立証。CR-01） | **恒久** | 外さない |
| G-4 verdict一致検査 | 同上（結論の再現性 AR-06） | **恒久** | 外さない |
| 再生成リトライ（最大2回） | 構造化出力・規則遵守の失敗率が非ゼロという前提で実装 | 暫定 | ガードレール違反率が**2週連続で0.5%未満**なら1回に減らす |
| 全件人手レビュー（AR-07） | 未知のすり抜け事例を集めるための立ち上げ期の運用 | 暫定 | 違反率0.5%未満かつ弁護士レビュー済みで、**抽出レビュー（10%）＋違反時全件**へ切替 |
| 用語注釈辞書（静的ブロック3） | 平易化はモデルが自然にできるが、**注釈の言い回しを一定に保つ**目的で保持 | 暫定 | 表現ゆらぎが問題にならないと確認できたら削除 |
| 「中学生が読める語彙」等の文体指示 | 現行モデルでも自然にできる可能性が高い（過剰指示の候補） | 暫定 | プロンプト短縮の実験で、削除しても文体が維持されるなら削除 |
| 出力を切り詰める処理／箇条書き強制 | **実装しない**（現行モデルは指示なしで構造化できる。過剰制御の典型） | ― | ― |
| 証券画像の抽出をLLMで行う | OCR専用サービスより実装が軽いという判断 | 暫定 | 抽出精度が要求水準に届かない場合はDocument AI等へ差し替え（OI-05） |

**運用ルール**：モデル（またはプロンプト版）を更新したら、**GT-01〜GT-10 と GR-01〜GR-07 を再実行**し、本表の「暫定」行を1つずつ見直す。見直し結果は改訂履歴に残す。
