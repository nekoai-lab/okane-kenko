# Tickets ─ Vertical Slice への分解

> `/to-tickets` 形式。SPEC.md を、単体で価値が出る最小の塊に切ったもの。
> 並べ方の原則：**H2（境界データの診断で「これなら動く」と感じるか）を、AIを実装する前に一度判定できる順序にする。**
> 版：v1.0（2026-08-17）

## 依存関係

```
T-01 算定エンジン ✅完了
  └→ T-02 アプリの器・デプロイ
        └→ T-03 入力ウィザード（保険以外）
              └→ T-04 現在の保険（3経路）★最大の離脱点
                    └→ T-05 結果画面 v1（AIなし・テンプレート文）  ◀── ここでH2の一次判定。立ち止まる
                          ├→ T-06 「分かること／分からないこと」＋次の一歩
                          ├→ T-07 AI言語化（プレースホルダ＋ストリーミング）
                          │     └→ T-08 ガードレール G-1〜G-6
                          ├→ T-09 計測イベント → 完走率・離脱率
                          └→ T-10 配偶者分の追加（世帯単位）
                                └→ T-11 運営レビュー画面
                                      └→ T-12 RAG（出典表示）
```

## 保険の「型」に触れる出力の在庫（OI-01 管轄・**現在ゼロ件**）

**2026-09-21 時点で、この製品は保険の型（収入保障型・掛け捨て定期など）に一切触れていない。**
全文検索で `収入保障` `掛け捨て` `定期保険` `終身保険` がコード・文言ともに0件（テストを除く）。

モック `result.html` の判断ポイント③には
「総額より期間の厚みで選びます。年々減っていく収入保障型が、形として合いやすい前提です」があるが、
**移植時に落とした**（`decisionPoints` は世帯ごとに事実を導出する設計で、
余剰のある世帯に保険の形の助言は成立しないため）。不足世帯の分岐にも型の行は無い。

**型の助言を入れるときの約束**

- **入れてよいのは1箇所だけ**：STEP4 の判断ポイント（`src/calc/decisionPoints.ts`）
- 特定商品・保険会社名は不可（CLAUDE.md「絶対にやらないこと」1）。**形の話にとどめる**
- **OI-01（保険業法の線引きの弁護士レビュー）の管轄**として、着手前にレビューを通す。
  形の話なので恐らく可だが、**この製品で唯一、募集の線に近づく出力**である
- 入れたら、この節に**文言そのもの**を転記して在庫にする
  （`guard.ts` の `RUSHING_WORDS` を一覧化しているのと同じ趣旨。場所を固定して見えるようにしておく）

## T-H 入力の不確かさをエンジンに通す（旧 T-H ＋ 旧 T-B を統合・2026-09-22）

**状態**：未着手。**着手はウォッチャー＋承認キュー（T-G 消化・期限 2026-10-05）のあと。**
**軸名**：必要額の判定（ニーズ軸）。

**統合の経緯**（2026-09-22 オーナー裁定）：
旧 T-B（`ample` のレンジ復活）を単独で実測したところ、**無風**だった。
ゴールデン10世帯は点入力なので6世帯とも動かず、代表3世帯でも「不足額そのもの」で読むと幅が1つも生まれない。
幅の材料（不確かな入力）が増えないかぎり T-B は効かないので、材料を増やす T-H に吸収した。
**`ample` のレンジ復活は、この仕組みの最初の消費者**という位置づけになる。
「6世帯の期待値が動く」という 2026-09-21 以来の想定は、**前提ごと撤回**する。

### 定義（オーナー承認済み・2026-09-22）

1. 不確かな入力（**回答帯**と、下の**未回答の幅仮置き**）のそれぞれに、
   「必要額を減らす端（**緩め端**）」と「増やす端（**厳しめ端**）」を定める。**入力ごとの方向表を仕様に書く**
2. 緩め端の前提一式でエンジンを1回、厳しめ端の前提一式で1回、**計2回まわす**
3. `レンジ = [緩め端の結果の low, 厳しめ端の結果の high]`。両端に葬儀床 `max(E4, ·)`
4. **端によって落ちる枝が違ってよい。** 生活費が帯の上端なら `sufficient` の 500〜700万、は
   別の枝の数字を借りているのではなく、**前提が外れたらそうなる**という答えそのもの
5. 判定（`verdict`）の分岐条件と `amplemarginRatio`・葬儀床の役割は変えない。変わるのは提示レンジだけ

実測（2026-09-22・組み替え世帯 `liv=lt30`）：点 `ample` 200万／帯の下端 `ample` 200万／
帯の上端 `sufficient` 500〜700万 → この定義でのレンジは **200〜700万**。

### 検算の置き方

各端は「その点での既存の式」を実行しているだけなので、**xlsx に帯の世界を新設しない**。
検算＝両端それぞれの点計算が既存の式と一致すること。
**ゴールデン10世帯は点入力のまま、算術の正本として残す**（期待値は動かない）。
帯の伝播はスナップショット・単体テスト側で固定する（合成世帯を xlsx に足さない先例どおり）。

**なぜ起票したか**（2026-09-21 オーナー指摘）：
STEP1 の推定ボックスの締め文が、モックどおり
「未回答は1つの数字で決めつけず、幅で計算して結果にも幅として残します」だったが、
**実装は未回答を1点で仮置きしている**ので、できていないことを約束していた。
締め文は実態に合わせて直した（`app/result/Step1.tsx`）。**約束のほうを実装に追いつかせるのがこのチケット。**

**現状の根拠**（点であることの確認）：

| 未回答 | いまの扱い | 出どころ |
|---|---|---|
| 年収「答えたくない」 | 300万円の1点 | `params/2026-08.yaml` `inputRanges.income.prefer_not` |
| 金融資産「分からない」 | 300万円の1点 | 同 `inputRanges.assets.unknown` |
| 生活費「年収から推定」 | 手取り × 0.75 ÷ 12 の1点 | `src/wizard/normalize.ts` の `monthlyLiving` 分岐 |
| 住宅ローン「分からない」 | 区分の代表値1点 | 同 `inputRanges.loan.unknown` |
| 進路「未定」 | 公立中心に固定 | `src/wizard/normalize.ts` の `educationPlan` 分岐 |

`src/wizard/normalize.ts` の `lookup()` は**数値を1つ返す口しか持たない**ので、
幅を通すには戻り値の形から変える必要がある。
幅を持っているのは回答帯（`inputRanges.monthlyLivingBand`・D-01）だけで、
あれは**答えた区分**の幅であって、未回答の幅ではない。

**未決**：未回答の幅の両端をどう置くか。区分の上下端を使うなら回答帯（D-01）と同じ作り方になるが、
「分からない」には区分そのものが無いので、**新しい当社基準が1つ増える**。
増やすなら `ownStandard` の在庫に載せる（公的出典なしと明示する）。
