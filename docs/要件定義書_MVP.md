## 0. この文書の読み方

本書は「**何を作るか・なぜ作るか・どこまでで完成とみなすか**」を定義する。画面・式・API・プロンプトなどの「どう作るか」は `機能仕様書_MVP.md` に分離した。

要件IDの体系：

- `FR-xx` 機能要件 / `NFR-xx` 非機能要件 / `CR-xx` 法令・コンプライアンス要件
- `DR-xx` データ要件 / `AR-xx` AI要件 / `PR-xx` 制度パラメータ要件
- `OI-xx` 未決事項（Open Issue）

優先度は MoSCoW：**M**=MVP必須 / **S**=あると強い / **C**=あってもよい / **W**=今回やらない。

## 1. 背景と目的

### 1.1 解く課題

生命保険の世帯加入率は9割弱、4割強が営業職員経由で「よく分からないまま」契約し、その後ほぼ見直されない。見直しのハードルは情報不足ではなく**感情**（また売り込まれるのが怖い／過去の契約を直視したくない／面倒）にある。既存の"無料見直し"は先が販売なので、この感情の壁を越えられない。

さらに公的保障が縮む方向に動いた（遺族厚生年金の有期化：2028年4月〜／高額療養費の自己負担上限引き上げ：2026年8月〜段階施行）。「自分でどれだけ背負うのか」が急に自分ごとになる一方、売り込みなしで"我が家の正解"を返す場所がない。

### 1.2 MVPの目的（何を確かめるために作るか）

本MVPは**売上を作るためではなく、事業の根が抜けていないかを確かめるために作る**。検証したい仮説は2つ：

- **H1（データ提供）** ユーザーは"薄すぎない"最小データを入力しきるか。特に「現在加入中の保険」で離脱しないか。
- **H2（価値）** 境界データだけの診断でも「これなら動く」と感じるか。「保険屋と同じ」「家計全体を見てほしい」にならないか。

H1・H2いずれかがNoなら、コードを書き足すのではなく**設計を戻す**。

### 1.3 事業の芯（要件の最終判断軸）

> 中立は、払い手が"商品の成約"でないときだけ本物になる。信頼の証明は「必要ないなら"入らなくていい"と言えること」。

要件の取捨で迷ったら、この芯を優先する。以下は**要件として禁止**する（アンチドリフト条項）：

| 禁止事項 | 理由 |
|---|---|
| 成約額・手数料を最適化する指標をプロダクトに持ち込む | 収益が「保険がどれだけ売れたか」に依存した瞬間、中立が死ぬ |
| 「売れた件数」をKPIダッシュボードに置く | KPIが行動を変える。売るがKPIになった時点で芯がずれる |
| 手数料の高い商品へ順位・表示を寄せる | 表示順は実質的な推奨。中立の外形が崩れる |
| 不安を煽って行動を促す文言 | 「煽りは無視してよい」と言える立場が資産。煽った瞬間に失う |

## 2. スコープ

### 2.1 やること（In Scope / MVP）

1. 社員が LINE / Web（LIFF）から**最小データを5分程度で入力**できる。
2. 入力から**必要死亡保障額**と**医療保障の過不足**を、**決定的な計算式（コード）**で算定する。
3. 算定結果を、**AIが世帯の事情に合わせて言語化**する（金額はAIに生成させない）。
4. 結果画面で「**足りている／ここだけ足す／むしろ減らせる**」を**内訳の因数分解つき**で提示する。
5. 制度改正（遺族年金の有期化・高額療養費）が**その世帯にいくら効くか／効かないか**を提示する。
6. 「**入らなくていい**」と言える箇所があれば必ず1つ提示する。
7. 診断の入力・出力・離脱地点を計測し、H1/H2の判定材料として蓄積する。

### 2.2 やらないこと（Out of Scope / 明示的に約束しない）

| やらないこと | 理由 |
|---|---|
| 家計最適化・キャッシュフロー設計・投資助言（"2階"の価値） | 継続的な支出データが必要でマネーフォワード等に勝てない。期待させると失望を生む。**結果画面の冒頭で「できません」と線を引く** |
| 特定商品の推奨・ランキング・比較表 | 媒介＝募集と見なされるリスク。CR-01参照 |
| プロダクト内での保険申込の完結、申込の代行 | 同上。MVPでは送客リンクすら出さない（2.3参照） |
| 保険会社・代理店からの手数料収受 | 芯（中立）が死ぬ |
| 法人管理コンソール／効果ダッシュボード | Phase1後半以降。MVPは「価値が届くか」の検証に集中 |
| 継続伴走・再診断の自動トリガー | Phase2（継続価値仮説の検証は別途、コードを書かない最小実験で行う） |
| 給与・年末調整データの法人システム連携 | Phase2。MVPは手入力で摩擦を実測する |
| ネイティブアプリ | LINE/LIFF＋Webで足りる |

### 2.3 段階（MVPの手前と後）

| 段階 | やること | 判定 |
|---|---|---|
| **Phase 0（コードを書かない）** | 紙／スプレッドシートの入力フォーム＋手計算の簡易診断で n1インタビュー2〜3名。法人ヒアリング1〜2社。スモークLP | H1/H2 と PEPM支払い意欲の一次判定。**ここがGOでなければ実装に入らない** |
| **Phase 1（本MVP）** | 本書の In Scope を実装。パイロット法人1社の社員に配布 | 完走率・"薄くなさ"の定量化、利用率 |
| **Phase 2（本書の対象外）** | 法人コンソール・ダッシュボード、再診断トリガー、法人データ連携、BigQuery本格活用 | 法人の継続契約（翌年も払うか） |

> **注意**：MVPは「送客しない」設計とする。事業計画では収益は法人PEPMであり送客手数料を取らないため、MVPで送客導線を持つ必要がない。導線を持たない＝募集行為から最も遠い位置に立てるので、規制と芯の両面で最も安全。

## 3. ステークホルダーとユーザー

| 区分 | 誰 | MVPでの関与 |
|---|---|---|
| 支払者 | 契約法人の人事・総務（福利厚生予算） | パイロット提供（MVPでは無償／実費）。効果指標は手作業レポートで代替 |
| 利用者（主） | 契約法人の従業員。**30〜40代・扶養あり・保険加入済み・直近2年見直していない** | 診断を最後まで通す |
| 利用者（副） | 従業員の配偶者 | MVPでは対象外（世帯情報は従業員が代表入力） |
| 運営 | 自社（2名想定） | 診断結果のレビュー、離脱分析 |
| 非対象 | 保険会社・代理店 | **MVPでは一切連携しない** |

**最も刺さる世帯（優先ペルソナ）** ― **2026-08-17 の10世帯テスト（`算定テスト_10世帯.xlsx`）で事業計画のターゲット表と食い違ったため、書き換えた。**

| 世帯 | 事業計画の想定 | テスト結果 | 刺さり方 |
|---|---|---|---|
| 30代 片働き・子あり | 2,000〜4,000万・◎ | 2,100〜3,100万 **不足** | **足りない**（想定どおり） |
| 自営・専業妻・子あり | （記載なし） | 1,600〜2,400万 **不足** | **足りない**（遺族厚生年金が出ない） |
| 40代 共働き・子2人 | 1,000〜2,000万・○ | **1,300万 減らせる** | **減らせる**（想定と逆） |
| 30代 共働き・団信あり | 500〜1,000万・△ | **1,800万 減らせる** | **減らせる**（想定と逆） |
| 独身・DINKs | ほぼ0〜300万・✕ | **保障不要／800万 減らせる** | **減らせる**（対象外ではない） |

**結論：不足が出るのは「配偶者が働いていない世帯」と「自営」だけ。それ以外はほぼ全部「減らせる」。**
19の死亡ケース中、不足は2件、減額余地ありが12件。減額余地の合計は10世帯で約1億2,000万円（1世帯平均1,200万円）。
→ **主戦場は「足りない層を埋める」ではなく「払いすぎを減らす」**。全世帯が対象になるので、対象は狭まるどころか広がる。

## 5. 機能要件（FR）

### 5.1 入力（診断ウィザード）

| ID | 要件 | 優先度 | 受入基準 |
|---|---|---|---|
| FR-01 | 家族構成（配偶者有無・子の人数と生年）をプルダウンで入力できる | M | 3クリック以内で完了 |
| FR-02 | 世帯年収を本人・配偶者別に**レンジ選択**で入力できる（1万円単位の入力を求めない） | M | 5択以上のレンジ。「答えたくない」を選べる |
| FR-03 | 金融資産をレンジ選択で入力できる | M | 〜100/〜300/〜500/〜1000/1000万+ |
| FR-04 | 住宅ローン等の負債を「有無＋残高レンジ＋団信の有無」で入力できる。団信を知らない人向けの1行説明を出す | M | 団信ありなら死亡時の住居費を0として扱う |
| FR-05 | 毎月の生活費をレンジ選択、または**年収からの自動推定**で入力できる | M | 自動推定を選べる。推定根拠を表示 |
| FR-06 | 就業形態（会社員/自営）と傷病手当金の認識を入力できる | M | 会社員/自営で公的保障の適用を切り替える |
| FR-07 | 現在加入中の保険を **①証券の写真アップ ②手入力 ③「分からない」** の3経路で入力できる | M | ③でも診断が完了する（FR-14） |
| FR-08 | 入力は途中保存され、離脱後も同一リンクから再開できる | M | 再訪時に入力済み項目が復元 |
| FR-09 | 現在の進捗（残り何問）を常時表示する | S | ステップインジケータ |
| FR-10 | 入力完了までの中位所要時間が**5分以内**の設問数に収める | M | 必須設問 12問以内 |
| FR-11 | 各設問の離脱・所要時間・「答えたくない」選択をイベントとして記録する | M | DR-04 |

> **FR-07 が事業の分かれ目**。ここで全員が離脱するなら境界データ診断は成立しない。3経路すべてを MVP で用意する（1経路だけでは検証にならない）。

### 5.2 算定（決定的ロジック）

| ID | 要件 | 優先度 | 受入基準 |
|---|---|---|---|
| FR-12 | 必要死亡保障額を、支出見込と収入・資産見込の差として算定し、**内訳を構造化データで返す** | M | 内訳項目ごとの金額が取得できる |
| FR-13 | 遺族基礎年金・遺族厚生年金・中高齢寡婦加算を、世帯構成と収入から算定する | M | 仕様書§4.3の式に一致 |
| FR-14 | 「現在の保険が分からない」場合も、必要保障額の算定と提示は成立させる（過不足判定のみ保留にする） | M | UC-03が完走する |
| FR-15 | 医療保障の過不足を、高額療養費の自己負担上限と金融資産から判定する | M | 仕様書§4.4 |
| FR-16 | 結果は**点ではなくレンジ**で提示する（例：約500〜1,000万円） | M | 単一値を断定しない |
| FR-17 | 制度改正（遺族厚生年金の有期化）が当該世帯に**該当するか／しないか**を判定して明示する | M | 子あり世帯には「直撃しない」と明示できる |
| FR-18 | 算定に使った制度パラメータの**版**を結果に紐づけて保存する | M | PR-03 |
| FR-19 | 「入らなくていい／減らせる」箇所を最低1つ検出する（検出できない場合はその旨を明示） | M | 過剰判定ロジックが動く |

### 5.3 言語化（AI）

| ID | 要件 | 優先度 | 受入基準 |
|---|---|---|---|
| FR-20 | 算定結果を、当該世帯の事情に触れながら平易な日本語で説明する | M | 中学生が読める語彙。専門用語には注釈 |
| FR-21 | 「なぜこの額か」を因数分解して説明する（遺族年金でX、貯蓄でY、だから足りないのはZだけ） | M | 内訳3要素以上に言及 |
| FR-22 | 公的制度に言及する箇所は**出典つき**にする（RAG） | M | 出典名＋参照年度を表示 |
| FR-23 | AIは**金額を生成しない**。文中の全数値は算定エンジンの出力を差し込む | M | AR-02のガードレールで検査 |
| FR-24 | 特定商品名の推奨、勧誘に相当する表現、不安を煽る表現を出力しない | M | AR-04の禁止リストで検査 |

### 5.4 結果提示

| ID | 要件 | 優先度 | 受入基準 |
|---|---|---|---|
| FR-25 | 結果は1画面（スクロール可）に収め、冒頭で結論（足りている／足す／減らせる）を出す | M | 冒頭で結論が読める |
| FR-26 | 冒頭に**「この診断で分かること／分からないこと」**を明示する（家計全体は扱わないと先に線を引く） | M | 2.2の割り切りを画面で表明 |

| FR-28a | **「次の一歩」の行動手順を示す**（ADR-001）。減らせる側＝現契約への減額依頼の手順／足りない側＝**まず勤務先の団体保険の確認**（窓口・受付時期つき） | M | 商品名なしで手順が完結する |
| FR-28b | 法人の団体保険情報が登録されていない場合は、FR-28aの「団体保険」をスキップし**「選ぶ基準」チェックリスト**にフォールバックする | M | 2経路が動作する |
| FR-28c | 「選ぶ基準」は**本人が「もっと知りたい」を押したときだけ開く**。押下をイベントとして記録する（CR-09の立証に使う） | M | 既定では表示されない |
| FR-28d | 本人が過剰・配偶者が不足のとき、「**世帯で見れば合計保険料を増やさずに解決できます**」まで示す。「付け替えましょう」「解約して入り直しましょう」とは言わない（ADR-007c） | M | 表現が禁止リストに一致しない |
| FR-29 | 結果に対する納得感（「これなら動く」）を1問で回収する | M | H2の定量指標（NPS的1問＋自由記述） |
| FR-30 | 結果URLは本人のみ閲覧可（認証必須）。共有は本人操作のPDF出力に限る | S | NFR-06 |

| NFR-06 | 認証・認可 | Identity Platform。法人テナント×社員のスコープ分離。他人の診断結果に到達できないこと |
| NFR-07 | 暗号化 | 保存時CMEK、通信TLS1.2以上。鍵はSecret Manager管理 |
| NFR-08 | 境界防御 | VPC Service Controls でデータ持ち出し経路を制限。管理系は最小権限IAM |

| NFR-11 | 保持・削除 | 保持期限を定め、本人操作で全削除できる。削除は分析用の集計値を除き物理削除 |
| NFR-12 | コスト | 1診断あたりAI変動費 10円以内（Gemini Flash相当・年20円/人の前提と整合） |
| NFR-13 | 可搬性 | GCPロックインを緩和するため、算定ロジックは外部サービス非依存の純粋関数として実装 |
| NFR-14 | アクセシビリティ | 文字コントラスト比 4.5:1 以上、文字サイズ拡大に追従 |
| NFR-15 | 運用 | エラー率・レイテンシ・ガードレール違反率をアラート化 |

## 7. 法令・コンプライアンス要件（CR）

判断軸は「Webか対面か」ではなく**「募集行為にあたるか」**。

| ID | 要件 | 根拠・意図 |
|---|---|---|
| CR-01 | 特定の保険商品を推奨・勧誘しない。商品名を含む比較・順位付けを出力しない | 媒介＝募集と見なされるため。MVPは募集の手前に完全に留まる |
| CR-02 | 重要事項（契約概要・注意喚起情報）の最終説明を行わない | 有資格プロセスの領域 |
| CR-03 | 保険の申込・申込の代行・送客を行わない（MVPは導線を持たない） | 2.3参照。最も安全な位置に立つ |
| CR-04 | 出力は「概算・一般的な情報提供」であることを毎回明示し、個別の契約判断は本人・有資格者に委ねる旨を表示する | 誤認防止 |
| CR-05 | 特定の金融商品（投資信託・個別銘柄等）の助言をしない。「浮いた保険料の使い道」は一般的な選択肢の列挙に留める | 金商法（投資助言・代理業）の線を越えないため |
| CR-06 | 効果や優位性について、根拠のない断定・最上級表現をしない | 景品表示法 |
| CR-07 | 個人データの取得目的・第三者提供の有無・保存期間を入力前に提示し、同意を取得する。**法人への個人単位の結果開示は行わない**（法人へは匿名集計のみ） | 個人情報保護法。社員の信頼が事業の前提 |
| CR-08 | 要配慮個人情報（健康・傷病歴）は原則取得しない。取得が避けられない場合は個別同意を取る | 同上 |
| CR-09 | 「募集の手前に留めた」ことを事後に立証できるログを残す（出力内容・提示リンク・本人操作の記録） | 将来Phase3で乗合代理店登録に進む場合の説明義務にも備える |
| CR-10 | インセンティブ（LINEギフト等）の設計は景品規制・法人側の課税処理と整合させる | MVPでは運営が手動配布とし、自動化はPhase2 |
| CR-11 | 2025年改正保険業法で強化された体制整備・意向把握の要求を、Phase3進出時の前提として設計に織り込む | ログ設計を今から仕込む（CR-09と同じ実装で満たす） |

## 9. AI要件（AR）

| ID | 要件 |
|---|---|
| AR-01 | **責務境界**：数値の算定＝コード、説明の言語化＝AI。AIは判断者ではなく翻訳者 |
| AR-02 | **数値ガードレール**：AI出力に含まれる数値トークンを抽出し、算定エンジンの出力集合に存在しない数値が含まれていたら出力を破棄し再生成する（2回失敗でテンプレート文にフォールバック） |
| AR-03 | **出典必須**：公的制度に言及する文には、RAGで引いた出典（文書名・年度・URL）を紐づける。引けなかった場合はその文を出さない |
| AR-04 | **禁止表現**：特定商品名／勧誘表現（「加入しましょう」等）／断定的な将来予測／不安を煽る表現／最上級表現を禁止リストで検査する |
| AR-05 | **「入らなくていい」の担保**：過剰と判定された箇所があれば必ず言及する。無い場合も「減らせる箇所は見つかりませんでした」と明示する（沈黙で誤解させない） |
| AR-06 | **再現性**：同一入力・同一パラメータ版で、結論（足りている/足す/減らせる）と全数値が一致すること（表現の揺れは許容） |
| AR-07 | **人のレビュー**：MVP期間中は全件を運営がレビューし、ガードレールをすり抜けた事例を禁止リストに追加する（人手前提を隠さない） |
| AR-08 | **プロンプト・モデル・パラメータの版管理**：出力に紐づけて保存し、再現・原因追跡ができること |
| AR-09 | AIへ渡す情報は算定済みの構造化データに限る。生の個人識別情報（氏名等）は渡さない |
| AR-10 | **AIに副作用を持たせない**。LLMにDB書き込み・外部送信・削除の手段を渡さず、出力は文章のみとする（不合格出力は破棄で済む状態を保つ） |
| AR-11 | プロンプトは「静的（規則・スキーマ）→ 動的（RAG結果・算定結果）」の順に組み立て、セッション中のモデル切り替えを行わない（再現性とコストの両立。仕様書§5.4） |
| AR-12 | **証券写真からの項目抽出（転記）と、結果の言語化（翻訳）を別のLLM呼び出しに分離する**。抽出失敗が説明文の推測に伝播しないこと |
| AR-13 | ガードレールのうち、①法令・信頼の立証のために存在するもの（数値照合・禁止語・結論一致）と、②現行モデルの弱点を補う暫定的なもの（リトライ回数・全件人手レビュー・文体指示）を**台帳で区別**し、モデル更新時に②のみ見直す（仕様書§12） |
| AR-14 | AR-07の全件レビューは、ガードレール違反率が2週連続0.5%未満になった時点で抽出レビューへ移行する（運用の陳腐化を放置しない） |

## 10. 制度パラメータ管理要件（PR）― 陳腐化対策

本プロダクトは公的制度の数値に強く依存し、その数値は**毎年度改定される／法改正で不連続に変わる**。ここを放置すると静かに誤った金額を出し続け、事業の芯（正直さ）を最も直接的に壊す。

| ID | 要件 |
|---|---|
| PR-01 | 制度パラメータ（年金額・給付率・自己負担上限・施行日など）を**コードから分離した設定ファイル**として管理する。ハードコード禁止 |
| PR-02 | 各パラメータに **値・単位・出典URL・根拠年度・有効期間・確認日・確認者** を持たせる。未確認値は `verified: false` として区別する |
| PR-03 | 診断結果には使用したパラメータ版（例 `2026.08`）を保存し、結果画面に算定基準日として表示する |
| PR-04 | 有効期間を過ぎたパラメータを使おうとしたら**起動時に警告し、期限切れが必須項目に及ぶ場合は診断を停止する**（黙って古い値で出さない） |
| PR-05 | 年金額改定（毎年1月公表・4月適用）と高額療養費の段階施行（2026年8月・2027年8月）を**カレンダー化して更新タスクを事前に立てる** |
| PR-06 | パラメータ更新時は、ゴールデンテストケース（仕様書§10.1）を再実行し、差分を記録する |
| PR-07 | RAGの知識ベースも同じ版管理下に置き、改正前の文書が引かれないよう有効期間メタデータでフィルタする |
| PR-08 | パラメータ版の有効化は**取り消せない操作**として扱う。汎用のDB操作やスクリプトで行わず、専用操作とし、①差分プレビュー ②ゴールデンテスト自動再実行の合格 ③実行者と承認者が別人（二人承認） ④監査ログ を必須とする（仕様書§7.1） |

### 11.2 検証KPI（作った後に測るもの）

| 仮説 | 指標 | GOライン |
|---|---|---|
| H1 データ提供 | 入力開始→結果到達の完走率 | **50%以上**（事業計画の完走率前提と整合） |
| H1 データ提供 | FR-07「現在の保険」ステップの離脱率 | **30%未満**。3経路のうち「分からない」選択率も記録 |
| H2 価値 | 結果への納得感（「これなら動く」に肯定） | **60%以上** |
| H2 価値 | 「家計全体を見てほしい」という反応の割合 | **40%未満**（超えたら1階の約束では足りない） |
| 中立の証明 | 「減らせる／入らなくていい」提示が出た診断の割合 | 記録のみ（0%なら判定ロジックを疑う） |

### 11.2b Phase0（n1 2〜3名）の GO/STOP ― 質的基準（ADR-013）

**11.2のKPIはPhase1（300人）でしか測れない。** 3人で完走率は測れないため、Phase0は**発言と行動のレベルで、n1を始める前に**基準を確定させる。

| 判定 | 条件（例。n1開始前に確定させること） |
|---|---|
| **GO** | 1人でも入力を完走し、かつ診断を見て「これなら動く」に相当する発言をした |
| **STOP／再設計** | 全員がS6「現在の保険」で証券を探しに行ったまま戻ってこない |
| **STOP／再設計** | 2人以上が「家計全体を見てほしい」「保険屋と同じ」と言った |
| **要注意（黄）** | 特定項目だけ拒否 → その項目を任意化するか、法人経由取得に回す判断材料にする |

> 定量は別経路（スモークLPの登録率）で取る。**下回ったときに何をするかを事前に決めていないGO/STOPは、必ず「サンプルが少ないから」で流れる。**

### 11.3 STOP／再設計トリガー

- 「現在の保険内容」で**ほぼ全員が離脱**する → 境界データ診断が成立しない。法人経由データ取得（Phase2の抜け道）へ設計を移す判断材料とする。
- 診断が「保険屋と同じ」「薄い」と受け取られる → 提示内容の設計（因数分解の見せ方）に戻る。実装追加では解決しない。
- 法人がPEPMを払う意思を示さない → 払い手を替える検討に戻る（芯は動かさない）。
