# 気づき通知(継続的な見直し) ─ 設計

> 版：2026-09-14。9/4の作戦(`2026-09-04_vol5-plan.md`)からの方針転換を反映。
> 位置づけ：okane-kenko(事業本体)を「お金ドクター」として育てる最初の一手であり、
> かつGoogle Cloudハッカソンvol5(提出締切10/15)の提出物そのものでもある。
> 9/5の作戦で「本体とは別に新アプリを作る」としていた前提は撤回し、**本体(main)に直接実装する**。

## 1. 背景・目的

okane-kenko(お金の健康診断)は一回の健康診断で終わる設計で、再訪の動機がない。
「お金ドクター」を名乗るには、扱う範囲を広げる(住宅ローン・教育費などを独立機能として追加する)のではなく、
**扱う範囲は保険のまま、継続性で"主治医らしさ"を出す**方向を採る。

範囲を広げない判断は、`docs/SPEC.md` の Out of Scope に既にある理由(「データ量でマネーフォワード等に勝てない」)と一致する。
一方、`docs/SPEC.md` の Out of Scope には「継続伴走・再診断の自動トリガー」がPhase2として明記されており、
**本設計はそのPhase2に着手するもの**である。SPEC.md側の記載更新は本設計の承認後に行う(§8参照)。

再訪の価値は「たまに見直さないと、という気づき」から生まれる。ただし気づきの中身が生々しい金額そのものだと、
ストレスを感じて逆に遠ざかる(行動経済学の ostrich effect)。**通知は"きっかけ"だけにし、金額は本人が能動的に選んだときだけ見せる。**

## 2. スコープ

- **フェーズ2a(今回の実装対象)**：世帯側の変化だけをトリガーにした通知ループを一通り作る。外部データ取得なし
- **フェーズ2b(次段階・別途設計)**：制度側の変化(候補：遺族年金)を1パラメータだけ自律的に監視する。ハッカソン審査基準②(自律性)を最も強く満たす部分
- **明示的にスコープ外**：住宅ローン・教育費などを独立機能として追加すること(既存のOut of Scope判断を維持)。マイページ／履歴画面(UI案C、見送り)

## 3. 全体構成(フェーズ2a)

```
Cloud Scheduler(週1・asia-northeast1)
  → POST /api/watch/run (Cloud Run・既存Next.jsアプリ内。認証はCloud SchedulerのOIDCトークン)
       1. 観察: Firestore の households を全件読む
       2. 判断: 各世帯で「子の学齢の節目に到達したか」を決定的なロジックで判定
          (AIは使わない。既存の教育費段階モデルの区分と一致させる)
       3. 行動: 該当があれば、固定テンプレート文言(イベント名のみ・数字なし)を
          Slack Incoming Webhook へ POST。金額の生成・判断はしない
       4. 記録: 実行内容を notice_log に書く(通知した/しなかった、両方を記録)
```

ADK等のエージェントフレームワークは使わない。既存のNext.js/TypeScriptアプリ内に1本のAPIルートとして実装する。
規約(第4条)の必須要件は既存の構成(Cloud Run・Gemini API)で充足済みであり、フレームワークの選定は審査対象外
(規約第7条の審査基準②は「振る舞い」を問うもので、実装手段は問わない)。

## 4. データモデル(Firestore・新規)

Phase A の「DBなし」を初めて崩す変更である(§8のADR起票対象)。保存するのはレンジ値のみで実額・氏名は持たない。

**`households/{householdId}`**

| フィールド | 内容 |
|---|---|
| `token` | マジックリンク用の固有トークン(URLに載せる。知っていれば開ける＝現行の本番URLと同じ信頼モデル) |
| `inputSnapshot` | ウィザードの正規化済み入力(レンジ値) |
| `lastDiagnosis` | 直近の結論・`coverageCurve`要点・使用パラメータ版・診断日時 |
| `consentedAt` | 同意画面で保存を選んだ日時 |
| `lastCheckedAt` | ウォッチャーが最後に確認した日時 |
| `lastNotifiedAt` | 最後に通知した日時(null可) |

**`notice_log/{id}`**(可観測性。審査基準②が明示的に求める部分)

| フィールド | 内容 |
|---|---|
| `runAt` | 実行日時 |
| `householdId` | 対象世帯への参照 |
| `triggerType` | `age_milestone`(2a)／`param_change`(2b・将来) |
| `triggerDetail` | 判定理由の人が読める要約 |
| `decision` | `notified` / `silent`(**変化なしで見送った実行も記録する**) |

## 5. 通知フロー(二段階同意)

1. Slackに固定テンプレート文言を投稿(例：「お子さんが7歳になりました」)。**数字は一切含めない。AIは使わない**(内容が固定文言＋日付だけのため生成の必要がない)
2. 通知内のリンク(`/notice/{token}`)を開くと、新規のミニ画面【UI案A】を表示。ここでもまだ金額は出さない。「詳しく見直す」ボタンのみ
3. ボタンを押すと既存の `/result` ページへ遷移し、フル診断(既存のAI言語化・ガードレール機構をそのまま使用)を表示する。余力があれば `/result` の冒頭に「前回(◯月◯日)からの変化」バナー【UI案B】を追加する

## 6. 初回保存の同意

診断完了(`/result` 表示)後、**独立した確認画面**を挟む【UI案2、確定】。

- 保存する内容(レンジ値の入力と結果の要点のみ)と、通知の頻度感(状況が変わったときだけ)を明記
- デフォルトは非保存(オプトイン)。同意なしに黙って保存しない
- 「保存しない」を選んでも `/result` の閲覧自体は妨げない

## 7. 削除・エラー処理

- 削除依頼があれば `households` ドキュメントを**即時物理削除**する(`docs/SPEC.md` US-10「7日以内」を即時で満たす)
- Slack投稿の失敗：1回リトライ。失敗したら `notice_log` に記録し、次回実行に持ち越さない(通知を溜め込んで一度に大量送信しない)
- 個別世帯の読み取り・判定エラー：該当世帯をスキップして記録し、他世帯の処理は継続する(1件の異常で全体を止めない)
- ウォッチャー自体の実行失敗：既存のCloud Run運用(ログ・監視)に準拠。新規のアラート基盤は作らない

## 8. テスト

- 学齢の節目到達の判定ロジックは、既存のゴールデンテストと同じ考え方で**境界値**(節目の前日・当日・翌日)を単体テストする
- `/api/watch/run` はFirestore・Slack送信をモックした統合テストを書く
- 実際のSlack送信・Firestore書き込みは、既存の `narrate.ts` の方針(実LLM呼び出しはローカルでは行わずデプロイ環境で検証)に合わせ、ローカルではモックのみとする
