## 3. 設計の裁定

- **単一サービス・同一プロセス。** ADK の別サービスは作らない。検算も HTTP 越しにせず、同じプロセスで回す（v1 の「2サービス」「HTTP検算口」は撤回）
  - 根拠(a)：レギュレーションの AI 要件は、製品が本番で使っている Gemini API で充足（9/14 文書の判断と一致）。D7 で主催の提出要件原文（<https://zenn.dev/hackathons/google-cloud-japan-ai-hackathon-vol5#rule>）に当てて確証を取る
  - 根拠(b)：審査軸②の「エージェントらしさ」は LLM の有無ではなく、**観察→判断→行動＋承認ゲートの構造**で立てる。
    「AIに金額を作らせない」を貫いた結果、巡回・抽出・検算が決定的になっているのは弱点ではなく主張
  - **LLM の正しい席は1つだけ残す**：影響レポートの言語化（数値は全部バインド・文章だけ Gemini・guard 経由。narrate 基盤の再利用）。
    「エージェントの中でも AI は言葉の係」という分担をデモで語れる。D6 の任意枠
- **ストレージは Firestore**（既存の提案・巡回記録を使う）
- **ツールは読み書き分離を厳守**：読み取り＝一次情報の取得（許可リスト・本文は untrusted）／params の読取／検算。書き込み＝承認キューに積むだけ
- **承認→適用の経路（既存実装どおり・維持）**：提案には適用可能な完全な yaml 差分を含める。承認ボタンは「approved」を記録するだけで、
  params の実変更はリポジトリへのコミット（push は人間）。「承認しない限り params が1バイトも変わらない」を画面と git 履歴の両方で示す
- **提案の yaml 差分の範囲**（2026-09-22 裁定）：提案の yaml 差分＝**適用後の params が自己整合する範囲**
  （値に加えて、`expires`・`pendingChange` の除去と note の更新まで）。値だけ変えて温存の期限と改正予定が残った yaml は、
  「温存が続いている」と自分で主張する矛盾ファイルになる。**コードの変更（test.todo の解消・失業カードの自白行）は提案に含めず、
  承認後の適用コミットで Claude Code が同時に行う**
- **一時状態（温存・保留・期限つき警告）は YAML コメントに書かない**（2026-09-22 裁定）。
  `pendingChange` / `expires` / `note` の構造化フィールドに置く。**コメントは恒久的な説明専用。**
  コメントは機械が管理できない場所なので、そこに状態を書くと差分が消し忘れる事故が構造的に再発する。
  `params/watch-sources.yaml` はテストで固定（`src/paramwatch/sources.test.ts`）。
  検出語は状態語（温存・保留・暫定・プレースホルダ・TODO・未反映）に限り、**⚠️ は検出語にしない**
  （恒久的だが重要な注意の印としても正当に使うため）。
  `params/2026-08.yaml` へのガード拡大は **D6 とセット**（多数回該当のプレースホルダ警告は D6 の昇格提案が消すので、
  先に広げると D6 前に赤くなる）。「暫定の幅」のコメントは 2026-09-22 に T-H の DoD へ移設済み。
  「⚠️ 置き方も当社基準」は恒久的な説明なので現状維持
- **エージェントの判断基準は既にあるものを使う**：params の sources（`effectiveFrom`・`expires`・`pendingChange`・`revisionCycle`）が「何を疑うべきか」の台帳。新しい判断ルールを発明しない
