# Spec ─ 社員向け「必要保障の見える化」診断（MVP / Phase1）

> `/to-spec` 形式。GitHub Issue としてそのまま起票できる粒度で書いてある。
> 上位：`要件定義書_MVP.md`（何を・なぜ）／`機能仕様書_MVP.md`（どう作るか）／`ADR.md`（決定の記録）
> 版：v1.0（2026-08-17、grill Q1〜Q9 と10世帯テストの結果を反映）

## Problem Statement

生命保険の世帯加入率は9割弱。4割強が営業職員経由で「よく分からないまま」契約し、その後ほぼ見直されない。見直しのハードルは情報不足ではなく**感情**にある——また売り込まれるのが怖い、過去の契約を直視したくない、面倒で時間もない。既存の"無料見直し"は先が販売なので、この壁を越えられない。

さらに公的保障が縮む方向に動いた（高額療養費の自己負担上限引き上げ：2026年8月〜段階施行／遺族厚生年金の有期化：2028年4月〜）。「自分でどれだけ背負うのか」が急に自分ごとになる一方で、**売り込みなしに"我が家の正解"を返す場所がない**。

10世帯の試算で分かったことがもう1つある。**遺族年金は多くの人が思っているより手厚く、共働き世帯ではほぼ充足する**。19の死亡ケースのうち不足は2件、減額余地ありが12件で、その合計は10世帯で約1億2,000万円だった。つまり実際に起きている問題は「保障が足りない」ではなく、**必要のない保障に払い続けている**ことである。

## Solution

法人の福利厚生として、社員が5分の入力で**必要保障額とその過不足**を根拠つきで受け取れるWebアプリを作る。

- **数値は決定的な計算式（コード）で算定し、AIは説明の言語化だけを担う。** AIに金額を生成させない。
- **「必要ないなら入らなくていい」と言い切る。** 減らせる箇所を必ず提示し、無ければ無いと明示する。
- **商品名を出さず、送客もしない。** 収益は法人からのPEPMで、保険成約手数料を取らない。だから中立が構造的に成立する。
- **次の一歩は示す。** 減らせる側は現契約への減額手順、足りない側はまず勤務先の団体保険。

MVPで確かめたい仮説は2つだけ。
- **H1**：ユーザーは"薄すぎない"最小データを入力しきるか（特に「現在の保険」で離脱しないか）
- **H2**：境界データだけの診断でも「これなら動く」と感じるか

どちらかがNoなら、コードを足すのではなく設計に戻る。

## User Stories

### 入力

**US-01 ─ 5分で終わる入力**
社員として、世帯の情報を5分程度で入力したい。なぜなら、面倒だと最後まで行き着かないから。
- Given 招待リンクから入った状態で
- When 必須設問（12問以内）に答えると
- Then 実額入力を一度も求められずに（すべてレンジ選択）、結果画面まで到達できる
- そして 各設問の所要時間と離脱がイベントとして記録される

**US-02 ─ 証券がなくても終われる**
社員として、保険証券が手元になくても診断を終わらせたい。なぜなら、証券を探しに行ったらそこで止まってしまうから。
- Given 「現在加入中の保険」のステップで
- When 「分からない」を選ぶと
- Then 診断は完走し、必要保障額は提示される
- そして 過不足の判定だけが保留になり、「証券が見つかったら再診断できます」と表示される

**US-03 ─ 中断して戻れる**
社員として、途中で中断しても同じリンクから続きを再開したい。なぜなら、証券を探しに席を立つことがあるから。
- Given 入力の途中で離脱した状態で
- When 同じリンクを開くと
- Then 入力済みの項目が復元されている

### 診断結果

**US-04 ─ なぜその額かが分かる**
社員として、必要保障額を内訳つきで知りたい。なぜなら、金額だけ言われても「保険屋と同じ」だと感じるから。
- Given 入力が完了した状態で
- When 結果画面を見ると
- Then 「遺族年金でX、貯蓄でY、だから足りないのはZだけ」という形で、内訳3要素以上に触れた説明が出る
- そして 金額は点ではなくレンジで示され、「概算・要精査」と算定基準日が明記されている

**US-05 ─ 減らせる箇所を教えてもらえる**
社員として、払いすぎている保障があるなら教えてほしい。なぜなら、それが一番すぐ効くから。
- Given 現在の保障が必要額を大きく上回るか、医療費を資産で賄える状態で
- When 結果画面を見ると
- Then 「この保険は減らせます／今日から要りません」と、浮く金額とともに提示される
- そして 減らせる箇所が無い場合も「今回、減らせる箇所は見つかりませんでした」と明示される（沈黙で誤解させない）

**US-06 ─ 煽りに惑わされない**
社員として、制度改正が自分の世帯に効くのかどうかを知りたい。なぜなら、ニュースで不安になっても自分に当てはまるか分からないから。
- Given 子のいる世帯で
- When 結果画面を見ると
- Then 「遺族厚生年金の5年有期化は子のいない配偶者が対象。この世帯は当面これまで通り」と明示される
- Given 子のいない世帯では
- Then 該当することと、その影響額が示される

**US-07 ─ 世帯として見てもらえる**
社員として、配偶者の分も含めた世帯の答えが知りたい。なぜなら、共働きだと片方だけ見ても意味がないから。
- Given 本人分の結果が出た状態で
- When 配偶者の保険を追加入力すると
- Then 本人・配偶者それぞれの死亡ケースと、世帯としての結論が1行で示される
- そして 本人が過剰・配偶者が不足の場合、「世帯で見れば合計保険料を増やさずに解決できます」と示される（「付け替えましょう」とは言わない）

**US-08 ─ 期待外れにならない**
社員として、この診断で分からないことを先に知りたい。なぜなら、家計全体を見てもらえると思って裏切られたくないから。
- Given 結果画面を開いたとき
- When 冒頭を読むと
- Then 「分かること／分からないこと」が明示され、家計全体の最適化は扱わないと先に書かれている

**US-09 ─ 次に何をすればいいか分かる**
社員として、診断のあと何をすればいいのか知りたい。なぜなら、「減らせます」と言われても手が動かないから。
- Given 減らせると判定された状態で
- Then 現契約のコールセンターに減額を依頼する手順が、商品名なしで示される
- Given 足りないと判定され、勤務先の団体保険情報が登録されている状態で
- Then 「まず勤務先の団体保険を確認してください」と、窓口・受付時期つきで示される
- Given 団体保険情報が未登録の場合
- Then 「選ぶ基準」のチェックリストにフォールバックする
- そして 「もっと知りたい」を押したときだけ選ぶ基準が開き、押下が記録される

**US-10 ─ データを消せる**
社員として、自分のデータを自分で消したい。なぜなら、家計と保険は機微な情報だから。
- When 削除を実行すると
- Then 削除される内容の一覧が提示され、確認のうえ7日以内に物理削除される

### 運営

**US-11 ─ AI出力を人が確認できる**
運営として、算定値とAI出力とガードレール判定を並べて確認したい。なぜなら、立ち上げ期はすり抜けを人が拾う必要があるから。
- Given 診断が完了した状態で
- When 運営レビュー画面を開くと
- Then 算定結果・AI出力・G-1〜G-6の判定・リトライ回数・フォールバック有無が1画面で見られる

**US-12 ─ パラメータを安全に更新できる**
運営として、制度パラメータをコード変更なしに更新したい。ただし誤って壊さないようにしたい。なぜなら、誤値は以後すべての診断を静かに間違わせるから。
- Given 新しいパラメータ版を登録した状態で
- When 有効化しようとすると
- Then 差分プレビューが表示され、ゴールデンテスト（10世帯・70件）に合格しないと有効化できない
- そして 実行者と承認者が別人であることが要求され、監査ログに残る

**US-13 ─ 検証の数字が取れる**
運営として、完走率と設問別の離脱率と納得感スコアを見たい。なぜなら、H1とH2はこれでしか判定できないから。

## Implementation Decisions

| 領域 | 決定 | 根拠 |
|---|---|---|
| 責務境界 | 数値＝コード、説明＝AI。AIには副作用（DB書込・外部送信）を一切持たせない | ADR-003 / AR-10 |
| 数値の受け渡し | AIはプレースホルダ（`{{necessaryAmount}}`）だけを書き、クライアントが算定結果を差し込む | ストリーミングと数値検査を両立させるため |
| 算定期間 | 一律「遺された配偶者が65歳まで」。就業状況で分岐せず、就労収入の控除を連続推定する | ADR-008（分岐すると境界で約1,800万円の崖ができる） |
| 就労収入 | 遺族の就労収入は全額差し引く | ADR-009 |
| 診断単位 | 世帯単位。ただし本人分で一度結果を返し、配偶者分は後から追加 | ADR-007 |
| 保険の保持 | 保険1件ごとに被保険者（本人／配偶者）を必須で持つ | 混同すると誤って「減らせる」と言う |
| パラメータ | コードから分離しYAMLで版管理。期限切れの中核パラメータでは診断を停止 | ADR-004 |
| 当社基準 | 公的出典のない係数は「当社基準」と明示し、結果画面で本人が動かせる | ADR-014 |
| インフラ | Phase A：Next.js on Vercel（`hnd1`＝東京）・DBなし → Phase B：+ Supabase（Tokyo）→ Phase D：GCP Cloud Run | 算定エンジンが純粋関数なので移行しても書き直さない（NFR-13） |
| ストリーミング | 算定結果を先に返し、AI言語化は逐次表示。AIが落ちても診断は成立する | NFR-01 / 可用性 |
| 商品情報 | RAGの知識ベースに商品情報を入れない | 商品を語れる状態にしない（CR-01） |

## Testing Decisions

| 対象 | 方法 | 合格条件 |
|---|---|---|
| 算定エンジン | ゴールデンテスト（10世帯・19死亡ケース） | 結論・レンジ・過不足・医療判定・改正該当がすべて一致 |
| 再現性 | 同一入力を10回実行 | 結論と全数値が一致（AR-06） |
| 芯の担保 | 「独身に上乗せを提示しない」「余剰が大きければ上乗せも不要と言い切る」「減らせる箇所が過半で検出される」をテスト化 | 全件パス |
| 数値ガードレール | 算定結果に無い数値を意図的に混入 | G-1 が100%検知（受入基準 A-2） |
| 禁止表現 | 商品名・勧誘表現・煽り表現を20ケース注入 | G-2 が全件検知、誤出力0件（A-3） |
| パラメータ期限 | 期限切れの版で診断を試行 | `503 PARAM_EXPIRED` で停止（A-7） |
| E2E | 入力→結果→アンケート、中断再開、全削除 | Playwright |
| セキュリティ | 他ユーザーの診断IDへのアクセス | 403。分析用DBに実額・氏名が入らないことをスキーマ検査 |
| コスト | 1診断あたりのトークン実測 | 10円以内（NFR-12） |

**運用ルール**：パラメータまたはモデル／プロンプト版を更新したら、ゴールデンテストとガードレールテストを必ず再実行し、差分を記録する。

## Out of Scope

| やらないこと | 理由 |
|---|---|
| 家計最適化・キャッシュフロー設計・投資助言 | データ量でマネーフォワード等に勝てない。期待させると失望を生むので、先に「やらない」と線を引く |
| 特定商品の推奨・比較表・ランキング・商品名の表示 | 媒介＝募集と見なされるリスク |
| 申込への送客リンク | 収益が送客に依存しない以上、持つ必要がない |
| 保険会社・代理店からの手数料収受 | 中立が死ぬ |
| 法人管理コンソール・効果ダッシュボード | Phase2 |
| 継続伴走・再診断の自動トリガー | Phase2。継続価値はまずコードを書かずに法人ヒアリングで確かめる |
| 給与・年末調整データの法人システム連携 | Phase2。MVPは手入力で摩擦を実測する |
| 就業不能・介護・学資の保障 | Phase2。MVPは死亡保障と医療保障のみ |
| ネイティブアプリ | LINE/LIFF＋Webで足りる |

## Further Notes

**この設計の弱点を正直に書いておく。**

- 「ほぼ全員が充足する」という結論は、**遺族の就労収入を全額差し引く設計に強く依存する**。差し引かない設計なら結果は真逆になる。FP実務でもここには幅がある。
- 10世帯は**架空の世帯**であり、実在世帯で検証していない。特にGT-08（夫年収400万・妻パート100万・子3歳・貯蓄100万）が充足になるのは直感に反するので、n1インタビューにこの条件に近い世帯を必ず1名入れる。
- 年金額は令和8年度の**報道値ベース**で `verified: false`。日本年金機構の一次情報で確定させるまで本番に出さない。
- 葬儀費用・教育費・入院期間・保険外費用は、公的／民間の調査に差し替える必要がある。
- 遺族生活費率0.70・手取り率0.80・末子独立後の最低就労推定100万円は、**公的出典が存在しない当社基準**。
- 保険業法の線引きは自社解釈である。**実装着手前に弁護士レビュー（OI-01）**。特に「団体保険の減額・追加加入の示唆」と「世帯で見れば合計保険料を増やさずに解決できる」という表現が乗換募集に当たらないかを確認する。
- 2名体制では「二人承認」が成立しない。代替統制が未設計（OI-09）。

**Phase0（コードを書かない検証）を先に通すこと。** n1インタビュー2〜3名の GO/STOP は、定量ではなく発言・行動レベルの質的基準で、開始前に文章として確定させる（ADR-013）。
