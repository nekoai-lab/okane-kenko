## 事業・戦略の語

| 用語 | 定義 | 補足・注意 |
|---|---|---|
| **芯 / 北極星** | 「不安定な人生に"頼れる"を取り戻す」。信頼の証明は**「必要ないなら入らなくていい」と言えること** | この語が出たら判断の最上位。他の要件と衝突したら芯が勝つ |
| **アンチドリフト** | 収益や指標が「保険がどれだけ売れたか」に依存し始めた状態を検知して戻すこと | 兆候＝成約額の最適化／「売る」がKPI化／手数料の高い商品への誘導 |
| **中立** | 払い手が「商品の成約に連動しない人」であること。**態度ではなく構造の話** | 「中立を心がける」は中立ではない。払い手が誰かで決まる |
| **B2B2C 福利厚生モデル** | 法人が福利厚生予算でPEPMを払い、社員は無料で使い、自社は保険手数料を取らない構造 | 中立が構造的に成立する唯一の形として2026-07に確定 |
| **PEPM** | Per Employee Per Month。従業員1人あたり月額課金 | 基本前提 500円／平均300人／社 |
| **1階（いっかい）** | **必要保障の過不足診断**。MVPで約束する範囲 | 境界データ（10問程度）で成立する |
| **2階（にかい）** | **家計最適化・ライフプラン・キャッシュフロー設計**。MVPでは約束しない | 継続的な支出データが要りマネーフォワード等に勝てない領域 |
| **境界データ** | 1階の診断に効く、境界のはっきりした最小データ（家族構成・収入レンジ・資産・負債・現在の保障・生活費） | 日々の支出明細は**含まない** |
| **薄くない診断** | 金額を断定するだけでなく、**因数分解して見せる**こと（遺族年金でX、貯蓄でY、だから足りないのはZだけ） | 「薄い」＝ユーザーが「保険屋と同じ」「家計全体を見てほしい」と感じた状態 |
| **完走率** | 入力開始 → 結果到達の割合。H1の主指標 | GOライン 50% |
| **H1 / H2** | H1＝ユーザーは最小データを出すか。H2＝境界データの診断で「これなら動く」と感じるか | MVPはこの2つを確かめるために作る |

## 規制・制度の語

| 用語 | 定義 | 補足・注意 |
|---|---|---|
| **募集行為** | 保険契約の締結の代理・媒介にあたる行為。判断軸は「Webか対面か」ではなく**これに当たるか** | 特定商品の推奨、重要事項の最終説明、申込の確定が典型 |
| **募集の手前** | 意向把握・必要保障の言語化・一般的な情報提供まで。MVPが立つ位置 | MVPは送客導線すら持たないことで、ここに完全に留まる |
| **乗合代理店登録** | 複数社の商品を比較・推奨するために必要な登録。説明義務が乗る | Phase3の将来像。MVPでは取らない |
| **遺族基礎年金** | 子のある配偶者・子に支給される国民年金の遺族給付 | 子が18歳到達年度末まで。令和8年度 基本額 約84.75万円（**要一次情報確認**） |
| **遺族厚生年金** | 厚生年金被保険者の死亡時に支給。報酬比例部分の3/4 | 被保険者月数が300未満なら**300月みなし** |
| **2028年改正（有期化）** | 遺族厚生年金が原則5年の有期給付になる改正（2028年4月〜） | **対象は「子のいない配偶者」**。子あり世帯は当面これまで通り＝「煽りは無視してよい」と言える根拠 |
| **中高齢寡婦加算** | 遺族基礎年金が終わった後、一定年齢の配偶者に加算される給付 | MVPの算式は粗い。要精査 |
| **高額療養費** | 医療費の自己負担に月額上限を設ける制度 | 2026年8月に上限引き上げ（第1段階）、2027年8月に13区分へ細分化予定 |
| **団信（団体信用生命保険）** | 住宅ローン契約者の死亡時にローン残債が消える保険 | **必要保障額を最も大きく動かす1項目**。ユーザーの多くが知らない |
| **傷病手当金** | 病気・けがで働けないときの健康保険の給付。**自営・フリーランスにはない** | 会社員/自営で公的保障が変わる分岐点 |

## プロダクト・実装の語

| 用語 | 定義 | 補足・注意 |
|---|---|---|
| **算定エンジン** | 必要保障額と医療保障の過不足を、決定的な計算式で出す純粋関数 | **金額はここでしか作らない** |
| **翻訳者（AIの役割）** | 算定エンジンの出力を、世帯の事情に合わせて平易な日本語に変えるだけの役割 | AIは判断者ではない。**数値を生成しない** |
| **ガードレール** | AI出力を機械的に検査する仕組み（G-1〜G-6） | 「恒久（法令立証のため）」と「暫定（モデルの弱点補完）」を台帳で区別する |
| **恒久ガードレール** | 数値照合(G-1)・禁止語検査(G-2)・結論一致(G-4)。モデルが賢くなっても外さない | 外す＝募集の手前に留まった証拠を失う |
| **暫定ガードレール** | リトライ回数・全件人手レビュー・文体指示。モデル更新時に見直す | 放置すると不要な処理を永久に抱える |
| **制度パラメータ** | 年金額・給付率・自己負担上限・施行日など、外部制度に由来する数値 | **コードから分離しYAMLで版管理**。値・出典・有効期限・確認済フラグを持つ |
| **パラメータ版** | 制度パラメータのスナップショット（例 `2026.08`） | 診断結果に必ず紐づけて保存する |
| **verified フラグ** | そのパラメータを一次情報で確認済みかどうか | `false` のまま本番に出さない |
| **ゴールデンテスト（GT）** | 世帯条件と期待値を固定した算定エンジンの回帰テスト | パラメータ更新時に必ず再実行。差分を記録 |
| **verdict** | 診断の結論。`sufficient`（足りている）/ `shortage`（足す）/ `excess`（減らせる）/ `adequate` | AI出力の結論がこれと一致しない場合は再生成（G-4） |
| **assumptions[]** | 欠損値を既定値で補ったとき、その事実と理由を記録する配列 | 「推定で埋めた」ことを結果画面で隠さないため |
| **取り消せない操作** | パラメータ版の有効化・本人データ全削除・BigQuery送出・インセンティブ配布 | 汎用スクリプトで実行しない。確認・監査・ゲートを付ける |
| **GCPプロジェクト / Firebaseプロジェクト** | **同じ1つの実体**。Firebase プロジェクトという別種の箱は存在せず、コンソールが2つあるだけ | Firebase 側で作っても GCP プロジェクトが1つできる。逆に GCP 側で作ったものは「Firebase を追加」するまで Firebase コンソールに出ない（後から追加できる。**外すのは面倒**なので迷ったら足さない） |
| **Admin SDK（`firebase-admin`）** | サーバーから Firestore を触る SDK。認証は ADC（Cloud Run の実行SA / `gcloud auth application-default login`） | 名前に Firebase と付くが **Firebase プロジェクト登録は不要**。本プロジェクトの `src/watch/store.firestore.ts` がこれ |
| **セキュリティルール** | ブラウザ・アプリが Firestore を**直接**叩くときの認可層 | **Admin SDK は完全にバイパスする**。本プロジェクトは `/api/watch/*` 経由でしか触らせないため、ルールを書く必要がそもそも無い。クライアントから直接読ませたくなった瞬間に Firebase 登録とルールが必須になる |

## 講義（Day14）由来の語

| 用語 | 定義 |
|---|---|
| **grill / grill-with-docs** | AI側が**一問一答で**要件の曖昧さを問い詰め、その過程を用語集とADRに残す進め方。人間が情報を渡すのではなく、AIに掘らせる |
| **to-spec** | grillで固めた要件を、実装につながるSpec（7セクション）に整理するスキル。GitHub Issueとして書き出す |
| **Spec の7セクション** | Problem Statement / Solution / User Stories / Implementation Decisions / Testing Decisions / Out of Scope / Further Notes |
| **ADR** | Architecture Decision Record。**重要で取り消しにくい決定**を、背景・選択肢・決定・結果の形で残す記録 |
| **Vertical Slice** | to-ticketsで仕様を分解するときの単位。画面からデータまで縦に貫く、単体で価値が出る最小の塊 |
